Executive Summary

MiroFish-Offline is a multi-agent social simulation engine built on the OASIS / CAMEL-AI framework with a Neo4j knowledge graph backend and a Vue 3 frontend. The baseline repository (forked from nikmcfly/MiroFish-Offline) ran with a local Ollama container and offered no runtime model control, no auth, no LLM call visibility, no live news enrichment, and no way to pause or reorder agents mid-simulation.

This report documents every change made across a three-phase sprint (15–20 June 2026) that transformed the project into a production-grade, multi-user, remotely accessible simulation platform under the Mu-Sigma brand.

Capabilities Delivered • Token-based multi-user authentication with role-based access (admin / user), login/register UI, and 1-week session tokens.
• Runtime LLM model switcher — pick any of 59 models from the remote Ollama server without restarting the app.
• Transparent agentic conversation log — every LLM prompt and response captured in a live, draggable floating panel.
• Live intelligence feed — web scraper pulls current headlines from HackerNews, BBC, Reuters, Reddit to seed simulations.
• Pause, rearrange & inject — pause a running simulation, reorder agents, tweak sliders, inject events, then resume.
• Bag ontology panel — entity types and edge types from Neo4j surfaced live in the simulation UI.
• Dark / light theme with persistent preference and Mu-Sigma branding throughout.
• Network portability fix — relative API paths so the app works from any IP/hostname.

  -p 7474:7474 -p 7687:7687 \

Appendix — Pydantic NER Upgrade Plan

Status: Implemented — ner_extractor.py updated (20 Jun 2026) The current prompt-based NER extractor has been replaced with a Pydantic structured-output pipeline (graphiti-style). The fallback path is preserved in full for models that do not support json_schema response_format.

A1. Current Approach — Limitations

The current NERExtractor sends a free-form JSON prompt to the LLM and retries up to 2× on invalid JSON. This is fragile: the LLM can hallucinate type names, produce malformed JSON, or include entities outside the ontology schema without any protocol-level enforcement.

A2. Proposed Approach — graphiti-style Pydantic Models

Graphiti's extraction pipeline defines entity types as pydantic.BaseModel subclasses and uses OpenAI's response_format / tool-calling structured output to extract instances. The LLM is constrained to the Pydantic schema at the protocol layer — invalid JSON and hallucinated field names become impossible.

For MiroFish, since the ontology is generated dynamically from user documents, we use pydantic.create_model() to build the models at runtime from the JSON ontology.

A3. Before vs After Comparison

A4. Implementation — What Was Changed

Only backend/app/storage/ner_extractor.py was modified (~240 lines). No other files touched. No new pip dependencies.

+_RelationItem(BaseModel) — fixed schema for all relation instances
+_make_entity_model(entity_def) → create_model() per ontology entity type
+_make_extraction_model(ontology) → top-level ExtractionResult with per-type List fields
+_extract_structured() — json_schema response_format + Pydantic model_validate()
+_pydantic_to_dict() — converts validated Pydantic object to {entities, relations} dict
~extract() → direct chat_json() with retriesextract() → _extract_structured() with fallback to _extract_prompt()
~_extract_prompt() (was the only path)_extract_prompt() (now the fallback path — code unchanged)

A5. Implementation Sketch

# ner_extractor.py — proposed replacement for _extract_with_prompt()
from pydantic import create_model, Field
from typing import Optional, List
import json

def _build_entity_model(entity_def: dict):
    """Build a Pydantic model from an ontology entity_type dict at runtime."""
    fields = {
        "entity_name": (str, Field(..., description="Canonical entity name")),
        "entity_type": (str, Field(entity_def["name"], description="Entity type")),
    }
    for attr in entity_def.get("attributes", []):
        fields[attr["name"]] = (
            Optional[str],
            Field(None, description=attr.get("description", attr["name"]))
        )
    return create_model(entity_def["name"], **fields)

def _build_extraction_model(ontology: dict):
    """Compose a top-level model holding lists of each entity type."""
    entity_models = {
        e["name"]: (List[_build_entity_model(e)], Field(default_factory=list))
        for e in ontology.get("entity_types", [])
    }
    return create_model("ExtractionResult", **entity_models)

# In NERExtractor.extract():
ExtractionModel = _build_extraction_model(ontology)
response = self.llm.client.beta.chat.completions.parse(
    model=self.llm.model,
    messages=messages,
    response_format=ExtractionModel,
)
result = response.choices[0].message.parsed
Prerequisite Ollama model must support function calling / tool use. Qwen2.5:32b, Qwen3:8b, Llama3.1+, Mistral-Nemo all support this. Verify with ollama show <model> and check for tools capability. Fallback: if parse() raises, the extractor can gracefully degrade to the current prompt-based method.
